## 5. 집·학교 오가며 작업하는 규칙

| 언제 | 명령어 |
|---|---|
| 작업 시작 | `git status` → 현재 브랜치·미커밋 변경 확인 → `git pull --ff-only` |
| 작업 끝 (매일, 컴퓨터 옮기기 전) | `git add .` → `git commit -m "내용"` → `git push` |
| 다른 컴퓨터에서 처음 | `git clone …` → `git checkout (작업 브랜치)` → `cd web` → **`npm ci`** |
| 다른 컴퓨터에서 받은 뒤 `package-lock.json`이 바뀐 날 | `cd web` → **`npm ci`** (잠금 파일 그대로 설치) |
| 패키지를 새로 추가·변경할 때 | `npm install (패키지)` → `package.json`과 `package-lock.json`을 **함께 커밋** |

- `node_modules`와 `.env.local`(Supabase 키 등)은 GitHub에 올리지 않음
- 학교 공용 컴퓨터면 작업 후 GitHub·Claude 로그인 정리

### B 이벤트 API v2 확정 안내 수신

- 최신 기준은 B의 `이벤트_기록_API_안내_A_v2.md`다. 안내 반영 커밋은 `feat/backend-setup`의 **`b63784a`**. 기존 `200b432`의 수정 전·분석가 확인 대기 상태는 대체되었다. 이번 갱신은 전달받은 v2 문서 기준이며 원격 코드·서버 테스트는 재검증하지 않았다.
- **DB 적용은 별도 확인 필요:** 마이그레이션 `20261118000008_event_record_type_placement.sql`을 B가 실제 Supabase에 적용해야 한다. 안내상 적용 전 `record_type`·`placement` 포함 요청은 500이다. 적용 완료와 실제 API 성공은 아직 확인하지 않았다.
- 서버 담당: `record_saved`, `material_confirmed` 구현 안내, `essay_saved`는 R08 개발 예정. 프론트에서 보내지 않는다.
- 화면 담당 5개: `record_started`, `writing_started`, `suggestion_shown`, `suggestion_selected`, `body_shared`. `POST /events`, Bearer 인증, 성공 204. 제안 이벤트 수신 준비와 R30 제안 기능 완성은 별개이며 R30은 개발 예정이다.
- **기록 시작 확정:** `record_type` 필수(free / qna). 화면 진입마다 1회, 이어 쓰기·새로고침·재진입 포함, 재렌더링 제외. 이어 쓰기의 `record_id`는 선택이며 해당 기록 방식과 일치해야 한다(불일치 422 `record_type_mismatch`).
- **글쓰기 시작 확정:** 직접은 편집기 진입, AI는 [초안 만들기] 첫 클릭. AI 생성 실패 후 재시도는 제외한다.
- **제안 노출·선택 확정:** 실제 보였을 때 한 화면에서 제안당 1회. 데이터만 수신하거나 스크롤로 다시 보인 경우는 보내지 않는다. `placement` 필수(home / suggestion_detail)로 홈·N130 구분. 선택은 [이 주제로 글쓰기] 클릭 시 1회, 빠른 연속 클릭 제외.
- **재전송·제안 경로 확정:** 네트워크 오류 등은 재전송하지 않고 401만 토큰 갱신 후 1회 재요청. 제안 경로는 `suggestion_id` 필수, 다른 경로에서는 보내면 422. 사용자 동작을 막지 않는다.
- **해석 확정:** 시작↔저장 개별 연결 ID는 MVP에서 도입하지 않는다. 정확한 완료율·이탈률 대신 **방식별 기록 화면 진입·저장 건수 비교**로 해석하고 한계를 명시한다.
- **문서·검증 반영 안내:** `material_count` 0~100(화면 선택 개수와 별개), 모르는 칸은 422, UUID 예시는 실제 내 ID로 교체, 담당·구현 상태 구분. 수정 대기 목록 23~27번에 반영했다.

### A 프론트 작업과 검증 범위

- 이벤트 전송용 이름을 화면 전용 5개로 제한하고 이벤트별 필수·허용 필드를 타입으로 표현한다.
- 현재 이벤트 목업은 검증 없이 성공한다. v2의 `record_type`·`placement` 필수 값과 기록 방식 일치 검사, `RULES`, UUID·허용값·범위·제안 경로 조건을 함께 반영한다. 서버 코드 반영 안내가 A 구현 완료를 뜻하지 않는다.
- 현재 `authHeaders()`는 빈 객체다. Bearer 토큰과 목록 19번의 401 갱신·연결 오류 구분을 연결한다. 204 빈 응답은 기존 클라이언트에서 처리 가능하다.
- `logEvent()`는 예외 대신 `ApiResult`를 반환하므로 `ok`를 확인한다. 실패로 화면 흐름을 막지 않고 개발 중 이벤트 이름·오류 코드만 확인한다. 본문·토큰은 로그에 남기지 않는다.
- 확인할 최소 시나리오: 합의한 진입·이어 쓰기 횟수, 재렌더링 중복 방지, 저장 재시도의 서버 이벤트 중복 방지, 필수·금지 필드·다른 사용자 ID 거절, 공유 성공만 기록(실제 모바일 포함), 이벤트 실패 시 화면 동작 유지.
- 이전 B 회신상 `record_saved`·`material_confirmed` 중복 방지와 필드·ID 검사 테스트가 존재한다. 이번 갱신에서는 v2 서버 코드·새 테스트 내용·실행 결과를 재검증하지 않았다.
- 다음 순서: A 타입·목업·화면을 v2에 맞춤 → B의 실제 Supabase 0008 적용 완료 확인 → 인증을 포함한 실제 이벤트 요청과 화면 시나리오 확인.
